# 0002 — Asynchronous, provider-neutral case generation

- **Status:** Accepted
- **Date:** 2026-10-26
- **Scope:** Phase 3–5 implementation
- **Related:** [`0001-deterministic-sample.md`](./0001-deterministic-sample.md)

## Context

The specification requires custom cases to be generated by a runtime AI provider without assuming that a provider, key, model, image feature, or video feature exists. It also requires validated output, bounded retries and timeouts, honest progress, recoverable failure states, duplicate-submission protection, and a playable sample when generation or media is unavailable.

A live generation attempt can take longer than a normal HTTP request, and the player needs to see progress. Returning only a final case would make progress impossible and risk proxy/client timeouts.

No provider credentials exist in this repository. The verified path must therefore work without a live provider, while leaving a real adapter available behind configuration.

## Decisions

### 1. Return `202` and poll a generation status

`POST /api/cases` with a custom brief creates a private case and a generation job, starts generation, and returns `202 Accepted` with a safe status view and `Location: /api/generation/:id`. The frontend polls the status endpoint and opens the case only when the job is `ready`.

A replayed request whose case is already ready returns `200` with the normal created-case view.

**Why:** Keeps the HTTP contract responsive, supports explicit stages, and avoids invented percentages. Progress reflects server-reported stages only.

### 2. Keep the provider boundary provider-neutral

`AIProvider.generateStructured` accepts prompts, a schema name/schema, a timeout, and optional context. Two adapters implement it:

- `mock` is the default and is deterministic and network-free.
- `openai-compatible` is optional and configured by `AI_BASE_URL`, `AI_MODEL`, and an optional `AI_API_KEY`.

The codebase does not assume a vendor, endpoint, model, key, or media capability. The adapter is verified with a mocked HTTP server, not a live endpoint.

**Why:** The application must remain runnable and testable with no credentials, and switching providers should not change game logic.

### 3. Validate before publishing; never publish partial or leaking output

Generated output passes four gates:

1. Strict Zod blueprint validation.
2. Brief-alignment checks (category, difficulty, timeline window, scenario terms).
3. Deterministic structural validation of mapped documents.
4. Persistence followed by a status transition to `ready`.

Any failure removes partial suspects, evidence, and solution documents and marks the case `failed`. The public timeline, evidence metadata, and hints are checked for culprit leakage.

**Why:** A syntactically valid but inconsistent or solution-leaking case would break the game and the public/private boundary.

### 4. Bounded retries with safe failure categories

Provider calls have a configured timeout and bounded retries with backoff for transient failures. Blueprint validation failures also trigger a bounded repair attempt. Credential failures are not retried. Player-visible errors are limited to `AI_PROVIDER_UNAVAILABLE`, `GENERATION_TIMEOUT`, `INVALID_AI_OUTPUT`, or `GENERATION_FAILED` with safe messages.

Raw provider responses, prompts, and secrets are never returned or stored on the job.

**Why:** Retries improve reliability, but unbounded retries and raw upstream errors create cost and disclosure risks.

### 5. Explicit idempotency semantics on the client

- The form is locked while a job is in flight or failed.
- A definitive failed generation clears the stored request key; retry uses a fresh key because the previous key maps to a failed case.
- An ambiguous network failure reuses the existing key, since the server may already have accepted the request and can safely replay it.
- Concurrent duplicate submissions with the same key share one case/job.

**Why:** Prevents duplicate generation charges and duplicate cases without making a genuine retry impossible.

### 6. In-process jobs with startup recovery

Generation currently runs in the API process, not a durable queue. At startup, `recoverInterruptedGenerations` marks unfinished cases/jobs as failed and deletes partial documents, so a restart produces a recoverable failure rather than an indefinite “pending” state.

**Why:** A durable queue is out of scope for this phase, but silently stuck jobs are not acceptable. This recovery assumes a single API process owns the database at startup.

### 7. Static fictional media only

`MEDIA_PROVIDER` supports `static` (approved fictional SVG) and `none` (written exhibit only). No live image or video adapter is implemented. The evidence renderer falls back to the written caption and interpretation if the image is missing or fails to load.

**Why:** The specification requires graceful degradation and forbids presenting fabricated media as real. The static asset is explicitly labeled.

### 8. Add committed browser and accessibility verification

Playwright runs the built app against an ephemeral MongoDB and the built API/frontend. It covers the full sample journey, correct and incorrect accusations, custom generation, generation failure/retry, mobile layout, and solution isolation. Axe scans the main screens at desktop and mobile widths and asserts zero WCAG A/AA violations.

**Why:** Component tests cannot verify the integrated browser flow, polling behavior, responsive layout, or accessibility tree.

## Consequences

- Generation jobs are not durable across horizontal scaling or a process crash/restart; startup recovery is a single-process safety net.
- A live provider still needs operational verification with real credentials before production use.
- Custom generation adds a new status endpoint and a stateful frontend form.
- Polling adds modest request volume; the status endpoint is ownership-checked and `no-store`.
- The static image is identical across generated cases; it is a labeled diagram, not case-specific generated media.
- No `SPEC.md` requirement was changed. These are implementation decisions within the existing product contract.

## Follow-ups

1. Verify the `openai-compatible` adapter against a selected live endpoint, model, and credentials; record timeout, retry, and output-quality behavior.
2. Replace the in-process worker with a durable queue and worker leases before multi-instance deployment.
3. Add a live media provider only when a real capability can be configured, labeled, and tested; keep text fallback.
4. Add load testing for polling and rate limits with a shared rate-limit store.
5. Add visual-regression coverage for the investigation and results screens.
